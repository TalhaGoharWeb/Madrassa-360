# RED-TEAM REPORT — Madrassa-360 — 2026-10-03

Independent adversarial re-audit. I did **not** trust the prior audit's
conclusions: every claim below was re-verified against the actual code in
this branch (`redesign/ux-v2`, worktree `~/workspace/madrassa-redesign-fix`).
Prior documents were read only to avoid re-implementing already-fixed items.

Threat model: a **mischievous normal user** (teacher harvesting other
schools' data, parent poking APIs with curl, accountant backdating
receipts), a **compromised low-privilege account**, and a **sophisticated
attacker** — in that order of likelihood.

Branch files only. **Nothing was deployed; nothing was applied to live
Supabase.** Migrations 045–046 are new files; Edge Function and Flutter
changes are uncommitted working-tree edits.

## 2. Fixed vulnerabilities

### RT-01 — Client-controlled timestamps on sync insert (MEDIUM)

- **SEVERITY:** Medium
- **ATTACK PATH:** Any tenant member with insert rights (e.g. an accountant
  with `fees.collect`) calls `sync_apply(entity='payments', op='insert')`
  with `created_at: '2020-01-01'` / `updated_at: '2099-01-01'` in the payload.
  The receipt is backdated (financial timeline forgery, audit-trail
  corruption); a far-future `updated_at` also poisons any client-side
  last-write-wins conflict resolution in the other device's favor.
- **ROOT CAUSE:** In `sync_apply` (033, re-declared in 034) the INSERT column
  allow-list excludes only
  `('id','revision','server_version','updated_by','deleted_at')` — the UPDATE
  branch excludes `created_at`/`updated_at` and stamps `updated_at = now()`,
  but INSERT trusted the payload.
- **AFFECTED COMPONENT:** `supabase/migrations/033_*`, `034_*` (`sync_apply`
  INSERT branch); every sync-whitelisted table.
- **FIX:** New migration **`046_sync_insert_timestamps.sql`**: a
  `BEFORE INSERT` trigger (`sync_force_server_timestamps()`) on every
  sync-whitelisted table carrying both columns overwrites `created_at` /
  `updated_at` with server `now()`. Database-layer fix — covers sync_apply
  **and** any direct PostgREST insert, present or future. Escape hatch
  `SET LOCAL app.preserve_timestamps = 'on'` for intentional historical
  backfills (seeds/migrations).
- **REGRESSION TEST:** `test/db/07_redteam_guards.sql` §(a)+(a2): structural
  (trigger present on all dual-timestamp sync tables) + behavioral
  (hostile `2001-01-01` timestamps overwritten; hatch honored). Staging-run.

### RT-02 — Broadcast email exposed every recipient's address (HIGH)

- **SEVERITY:** High (PII disclosure)
- **ATTACK PATH:** A teacher (or any holder of `notifications.send`)
  broadcasts a notice to all parents. `send-notification` put every
  recipient in the SMTP `To:` header — **every parent receives every other
  parent's email address**. Harvestable at scale with 30 broadcasts/hour.
- **ROOT CAUSE:** `to: addresses` in the Resend call; HTML was escaped but
  recipient privacy was never addressed (previously deferred as "BCC
  decision").
- **AFFECTED COMPONENT:** `supabase/functions/send-notification/index.ts`
  (email branch).
- **FIX:** Recipients moved to `bcc:`; `to:` is the sender address. One API
  call, zero cross-recipient disclosure. (Push path was already per-token.)
- **REGRESSION TEST:** Code-level (payload shape); `deno check` + `deno lint`
  clean. No automated test exists for the Resend payload — recommended
  follow-up: extract a `buildEmailPayload()` helper and unit-test it.

### RT-03 — Rate limiting failed open everywhere (MEDIUM)

- **SEVERITY:** Medium
- **ATTACK PATH:** `guard.ts`'s `rateLimit()` had **no backing table** —
  every check threw, was caught, and **failed open** with a log line. Only
  `send-notification` even called it. A compromised manager account could
  script `manage-users` (mass deactivation / password resets / user
  enumeration), `export-tenant` (bulk PII exfiltration, 21 table scans per
  call), `upload-image` (5 MiB × N storage exhaustion), `provision-tenant`
  (tenant flood) at full speed.
- **ROOT CAUSE:** DDL documented in a comment but never shipped as a
  migration; rate-limit wiring never extended beyond one function.
- **AFFECTED COMPONENT:** `supabase/functions/_shared/guard.ts`,
  all six Edge Functions.
- **FIX:** New migration **`045_edge_rate_limits.sql`** (table + index, RLS
  enabled with **zero policies** = service-role only, exactly as `guard.ts`
  specifies; comment updated). Wired `rateLimit()` into every function:
  `manage-users` 120/hr per caller (+ tighter 30/hr on `create_user`),
  `export-tenant` 5/hr, `upload-image` 60/hr, `provision-tenant` 10/hr,
  `manage-tenant` 30/hr, `send-notification` already had 30/hr broadcast /
  120/hr targeted (now actually enforced).
- **REGRESSION TEST:** `test/db/07_redteam_guards.sql` §(b): table/columns/
  index present, RLS on, zero policies, fixed-window count query works.
  `deno check` + `deno lint` clean on all six functions.

### RT-04 — upload-image path broke storage RLS + orphaned files (MEDIUM)

- **SEVERITY:** Medium (authorization regression + storage abuse)
- **ATTACK PATH / FAILURE:** `upload-image` wrote
  `<tenant_id>/<kind>-<ts>-<rand>.<ext>`, but migration 040's storage RLS
  policies parse `<tenant_id>/students/<student_id>.<ext>`
  (`storage_photo_student_id()` reads `foldername[3]`). Consequences: (1) the
  parent-of-student SELECT exception **never matches** new uploads — parents
  lose photo access once the client switches to this function; (2) every
  re-upload orphans the previous file (unbounded storage growth, attacker-
  amortizable).
- **ROOT CAUSE:** Path convention invented in the function disagreed with
  the convention the RLS policies were written against (040 header documents
  the app's convention).
- **AFFECTED COMPONENT:** `supabase/functions/upload-image/index.ts`.
- **FIX:** Deterministic policy-matching paths —
  `<tenant_id>/logo.<ext>`, `<tenant_id>/students/<id>.<ext>`,
  `<tenant_id>/staff/<id>.<ext>` — with `upsert: true` (replacement is
  atomic, no orphans); when the extension changes, the previous file (only
  if it parses as a same-bucket path) is deleted best-effort. Plus the
  60/hr rate limit from RT-03.
- **REGRESSION TEST:** `test/db/07_redteam_guards.sql` §(c): 040 helpers
  parse the deterministic convention; `deno check` + `deno lint` clean.

### RT-06 — CSV formula injection (MEDIUM)

- **SEVERITY:** Medium
- **ATTACK PATH:** Attacker (anyone who can get a row synced — e.g. a
  student name, or a compromised low-privilege account) stores
  `=cmd|'/c calc'!A0` as a name. The accountant exports the fee register
  to CSV and opens it in Excel → formula executes (classic CVE-2018-1050
  class; DDE payloads run without macro warnings in older Excel).
- **ROOT CAUSE:** `CsvExport._esc` quoted cells but never neutralized
  formula-trigger prefixes (`=`, `+`, `-`, `@`, tab, CR).
- **AFFECTED COMPONENT:** `lib/core/reports/export/csv_export.dart`.
- **FIX:** Cells starting with a trigger character get Excel's text-marker
  apostrophe prefix (invisible in Excel, forces text interpretation),
  applied before quoting. (The XLSX exporter was verified safe — it uses
  `TextCellValue`, written as inline strings, never formulas.)
- **REGRESSION TEST:** `test/unit/redteam/csv_formula_guard_test.dart` —
  6/6 pass (`flutter test`), `flutter analyze` clean.

## 4. Security assumptions

1. **Supabase platform**: Auth JWT signatures, RLS evaluation, Storage
   isolation, and Edge Function secret storage are trusted. A Supabase
   platform breach is out of scope.
2. **`auth.uid()` integrity**: every DB check keys off the JWT-derived uid;
   assumes the legacy JWT secret is rotated and old keys revoked (blocker §5).
3. **Service-role key secrecy**: it lives only in Edge Function env. Any
   leak = full bypass (by design of the architecture).
4. **Client clock is untrusted**: conflict/timestamp logic uses server
   `now()` after this fix (046); no security decision depends on device time.
5. **Fail-open rate limiting is acceptable**: on DB outage the limiter logs
   and allows (documented in `guard.ts`) — availability over throttling.
6. **Device sandbox**: secure storage (Keychain/EncryptedSharedPreferences)
   and `allowBackup=false` are trusted; a rooted/jailbroken device can read
   the plaintext SQLite DB (RT-10).
7. **Third parties**: FCM and Resend are trusted with notification content;
   email is inherently non-confidential in transit to the provider.
8. **UUID unguessability**: row IDs are 128-bit random; existence oracles
   that require knowing a UUID are treated as non-issues.

## 6. Recommended future hardening

1. **App Links / Universal Links** (RT-07): verified-HTTPS deep links for
   auth recovery; removes the custom-scheme interception vector.
2. **SQLCipher** for the local Drift database (RT-10).
3. **Extract `buildEmailPayload()`** in send-notification and add a Deno
   unit test pinning the BCC invariant (RT-02 regression test gap).
4. **Anomaly alerting**: export-tenant calls, mass `set_active`/`delete_user`,
   and rate-limit 429 spikes should page, not just log.
5. **Extend 046's approach to UPDATE**: server-stamp `updated_at` on direct
   PostgREST updates or prove RLS policies already prevent spoofing (RT-12).
6. **Fix `list_users` N+1** (RT-11): single query joining auth users, or
   paginate server-side with a join.
7. **CORS tightening** if a web client ever ships (RT-08): allow-list
   origins instead of `*`.
8. **PostgREST body-size / statement-timeout review** for direct RPC abuse
   (RT-09) at the Supabase project level.
9. **Scheduled `edge_rate_limits` cleanup** (pg_cron or scheduled function)
   — the opportunistic 5% cleanup works but a janitor job is cleaner.
10. **Periodic re-run of `test/db/*.sql` against staging** in CI (nightly)
    so trigger/policy drift fails loudly.
