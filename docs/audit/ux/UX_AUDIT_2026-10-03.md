# UX Audit — Madrassa-360

**Date:** 2026-10-03 · **Branch:** `redesign/ux-v2` · **Commit audited:** `945dce7` (working tree at audit time)
**Scope:** Full interface review — navigation, IA, consistency, typography, states, forms, search/filters/tables, dashboards, responsiveness, keyboard/a11y, RTL, localization.
**Method:** Static code review of `lib/presentation/` (99 screens), `lib/core/design/` (m360 design system), `lib/core/constants/` — no device testing. Three parallel review tracks (navigation/IA, forms/states, typography/RTL/a11y) plus independent verification of key claims by the lead auditor. Severity = usability impact on real users (admins, teachers, accountants, parents on Android phones; platform admins on Windows desktop).
**Rule followed:** No redesign for visual novelty. Every recommendation is a minimal usability fix preserving established functionality.

## CRITICAL

### C1 — Student admission/edit dialogs: submit with missing required fields fails SILENTLY
- **Location:** `lib/presentation/screens/students/student_dialogs.dart:252` (`_submitNewAdmission`), `:418` (edit)
- **Problem:** The submit guard does a silent `return` when name/father-name are empty. The fields carry `validator:` callbacks, but there is **no `Form` widget and no `validate()` call anywhere in the file** — the validators are dead code, and the design-system `M360Dialog` doesn't wrap content in a `Form` either.
- **Who it hurts:** Every admin doing admissions — the highest-frequency data-entry flow in the app.
- **Scenario:** Admin fills only the phone number, taps «داخلہ لیں» — nothing happens, no message. They tap repeatedly, assume the app froze or the button is broken, and may abandon a real admission.
- **Minimal fix:** Wrap the dialog content in a `Form` with a `GlobalKey<FormState>` and call `validate()` on submit. The proven pattern already exists in-repo: `lib/presentation/screens/hostel/hostel_forms.dart:97` and `auth/login_screen.dart:85`.

### C2 — Android system-back on any shell destination exits the app (no nav history)
- **Location:** `lib/presentation/shell/app_shell.dart` — `_select()` only `setState`s `_selectedId`; grep confirms no `PopScope`/`WillPopScope` anywhere in the shell (the only `PopScope` in the repo is `update_service.dart:342`).
- **Problem:** The shell swaps destinations in place with no navigation history stack. Pressing the Android system back button on any non-dashboard destination closes the app instead of returning to the previous screen.
- **Who it hurts:** Every Android user — back is the most-used navigation gesture on the platform.
- **Scenario:** Accountant opens مالی → واجبات, presses back to return to the dashboard → the app closes. They relaunch and re-navigate.
- **Minimal fix:** Add `PopScope` in `AppShell`: when `_selectedId != 'dashboard'`, intercept the back press and route to the previous destination (or dashboard), instead of popping the app route.

## HIGH

### H1 — Class filter chips in the student list can never match — filter silently empties the list
- **Location:** `lib/presentation/screens/admin/student_list_screen.dart` (`_FilterChips` ~:380, `_applyFilters` :128); `student_dialogs.dart:296`
- **Problem:** Chips are built from hard-coded `StudentDialogs.classOptions` (e.g. `'درجہ اولیٰ (اول سال)'`), but on save `className` is written from the real darja row's `nameUrdu` (no parenthetical). The equality check `s.className == _selectedClass` can never be true.
- **Who it hurts:** Admins browsing students by class.
- **Scenario:** Admin taps the «درجہ اولیٰ» chip → the whole list vanishes with «کوئی طالب علم نہیں ملا» even though students exist. Looks exactly like data loss.
- **Minimal fix:** Build the chips from the real darja rows (`safeDarjaListProvider` — the same source as the admission form's darja picker), not `classOptions`.

### H2 — Results entry: invalid marks are silently dropped, then a success message claims they saved
- **Location:** `lib/presentation/screens/teacher/results_screen.dart:1056` (`_saveEntryResults`)
- **Problem:** `if (value == null || value < 0) continue;` silently skips bad rows, then `showM360SnackBar(context, '${marks.length} نتائج محفوظ ہو گئے')` claims success. Also no upper bound — 150/100 is accepted.
- **Who it hurts:** Teachers entering bulk marks; students whose marks silently vanish.
- **Scenario:** Teacher types "abc" (slip on the numeric keyboard) for two students, taps «نتائج محفوظ کریں» → snackbar says saved; the bad rows never persist and nothing flags them. Report cards go out wrong.
- **Minimal fix:** Validate all fields before saving; abort and name the offending rows (first offending student in the snackbar, or inline field errors). Reject `value > totalMarks`.

### H3 — Two navigation paradigms mixed: pushed screens can be dead-ends on desktop
- **Location:** `lib/core/design/m360_navigation.dart:18` (`pushM360Page`); dashboards (`accountant_dashboard.dart:107`, `principal_dashboard.dart`); `_withBack` pattern in `fee_management_screen.dart:66`, `student_list_screen.dart:42`
- **Problem:** The shell swaps destinations in place, but several dashboards `pushM360Page` detail screens onto the Navigator. Pushed routes only get a back affordance if the destination implements the `_withBack` pattern (7 screens do). `finance_hub_screen.dart` and `attendance_screen.dart` do **not** — and the accountant dashboard pushes `FinanceHubScreen` directly. On Android the system back button rescues the user; on **Windows desktop there is no system back button**, so a pushed screen without `_withBack` is a dead end. Meanwhile the teacher dashboard already uses the correct in-shell pattern (`requestShellNav`).
- **Who it hurts:** Desktop (Windows) users navigating from dashboards — the platform-admin/accountant audience.
- **Scenario:** On Windows, accountant taps a dashboard card → lands on the finance hub → no back arrow anywhere → must use the rail/drawer to navigate away, losing context.
- **Minimal fix:** (1) Audit every `pushM360Page` destination for `_withBack` and add it where missing (one-line pattern, already proven); (2) standardize dashboard CTAs on `requestShellNav` (in-shell navigation) like the teacher dashboard, reserving pushes for true detail overlays.

### H4 — Duplicate quick-action tiles on the accountant dashboard
- **Location:** `lib/presentation/screens/dashboards/accountant_dashboard.dart` (`_FinanceQuickActions`)
- **Problem:** «فیس وصول کریں» **and** «رسید بنائیں» both open `FeeManagementScreen()` (identical target); «حساب دیکھیں» **and** «تفصیلی حسابات» both open `FinanceHubScreen(section: FinanceSection.ledger)`. Seven tiles where four would do — choice paralysis on the role's home screen.
- **Who it hurts:** Accountants, daily.
- **Scenario:** New accountant wonders what the difference is between «رسید بنائیں» and «فیس وصول کریں», tries both, lands in the same place twice, loses trust in the IA.
- **Minimal fix:** Drop «رسید بنائیں» (receipts are created inside the fee screen); merge the two ledger tiles into one.

### H5 — Parent's primary task needs 4 taps on mobile; mobile primaries collapse for parents
- **Location:** `lib/presentation/shell/nav_destinations.dart` (`kMobilePrimaryIds` = dashboard, student-list, attendance, student_fees); `parent/fee_history_screen.dart` (`parent-fees`)
- **Problem:** A parent holds none of the last three primaries' permissions, so their bottom nav degrades to ڈیش بورڈ + مزید. Their one real task — «فیس کا ریکارڈ» — requires مزید → drawer → scroll → فیس کا ریکارڈ (4 taps, two of them discovery).
- **Who it hurts:** Parents — the least tech-comfortable user group, on phones.
- **Scenario:** A parent who only wants to check "did my payment post?" must hunt through a drawer of destinations they can't use.
- **Minimal fix:** Make the mobile primary set role-aware (e.g. parent → `parent-fees` as a primary tab), or promote the fee record to a first-class card on the parent's dashboard in `role_home.dart`.

### H6 — Screen-reader support is nearly absent
- **Location:** Repo-wide: only 2 files under `lib/presentation/` use `Semantics(`, 9 use `semanticLabel` — across 99 screens.
- **Problem:** Interactive elements (dashboard stat cards with `onTap`, icon-only buttons, status chips) expose no accessible names. Status chips do carry `Semantics(label: 'حالت: …')` (`m360_status.dart`) and `M360IconButton` requires a tooltip — the plumbing exists but adoption is ~2%.
- **Who it hurts:** Blind/low-vision users; also fails Play Store accessibility expectations.
- **Scenario:** A visually-impaired admin using TalkBack hears "button, button, button" on the dashboard's tappable stat cards.
- **Minimal fix:** Add `Semantics` labels to tappable dashboard cards and icon-only actions first (highest-traffic surfaces), then expand per screen. No visual change.

### H7 — Dashboard stat-card values overflow at 360px for large amounts
- **Location:** `lib/core/design/m360_cards.dart:210–219` (`M360StatCard`); seen on `accountant_dashboard.dart:110–135`
- **Problem:** The value renders at 28sp bold Nastaleeq with **no `overflow`, `maxLines`, or `FittedBox`**, inside a half-width card (~155px usable). A real value like `Rs 1,25,00,000` (~260px) overflows → yellow/black stripes. (Side note: the comment at `m360_cards.dart:134` claims the value renders in Naskh, but the code uses Nastaleeq `bodyLarge` — stale comment.)
- **Who it hurts:** Every accountant/admin on a phone once balances grow.
- **Scenario:** Month-end: the «آج کی وصولی» card shows overflow stripes instead of the collection total.
- **Minimal fix:** Wrap the value in `FittedBox(fit: BoxFit.scaleDown)` (preferred — never hides digits) and fix the stale comment.

### H8 — Body/small Urdu text set in Nastaleeq below the file's own legibility floor
- **Location:** `lib/core/constants/app_typography.dart:124–140` (`bodySmall` 14sp, `labelSmall` **12sp**); the file's own `labelNastaliq` comment states *"Nastaleeq stays legible at >= 15sp"*
- **Problem:** The smallest, highest-density Urdu in the app (status chips `m360_status.dart:165`, tab labels, form hints) renders at 12–14sp Nastaleeq — below the documented legibility threshold. Nastaleeq's tall glyphs and nuqtas degrade fast at small sizes.
- **Who it hurts:** Older/low-vision staff reading fee statuses and form hints.
- **Scenario:** A 55-year-old accountant squints at 12sp Nastaleeq status chips on «واجبات» rows.
- **Minimal fix:** Raise `labelSmall` to 15sp and `bodySmall` 14→15sp. **Open product question** (flagged by the auditor, matches the standing "Nastaleeq everywhere" brand decision): confirm whether 15sp floor is acceptable or small text should switch to Naskh instead — do not change silently.

## MEDIUM

### M1 — Back affordance is "home", not "back"; breadcrumb is decorative
- **Location:** `lib/presentation/shell/app_shell.dart` (`_ShellAppBar` — arrow always `onSelect('dashboard')`, tooltip «واپس ڈیش بورڈ»)
- **Problem:** The arrow doesn't go back one step — it goes home. The breadcrumb (group › destination) is a single non-interactive level. Users can't retrace one step in-shell.
- **Fix:** Keep a tiny destination-history stack in `AppShell`; the arrow pops it (falling back to dashboard when empty). Relabel honestly.

### M2 — «پلیٹ فارم» quick action visible to every parent/student, then errors
- **Location:** `lib/presentation/screens/dashboards/role_home.dart` (`GenericDashboardScreen`)
- **Problem:** The tile renders unconditionally; the platform-admin check happens *after* tap (`fetchPlatformAdminRole()` → snackbar «آپ کو رسائی حاصل نہیں»). A dead-end tile for the majority of users.
- **Fix:** Resolve the platform role once in the dashboard build and hide the tile when null.

### M3 — Logout is buried with exactly one path
- **Location:** `lib/presentation/shell/nav_destinations.dart` ('logout' at the bottom of the ترتیبات group)
- **Problem:** Mobile path: مزید → drawer → scroll past up to 6 groups → ترتیبات → لاگ آؤٹ. The rail `_UserFooter` and profile chip have no logout affordance; the command palette explicitly excludes it. The user's standing rule is "logout always one tap".
- **Fix:** Add a logout icon-button next to the gear in the rail `_UserFooter` (desktop/drawer) and in the profile chip overflow.

### M4 — Command-palette search results don't deep-link
- **Location:** `lib/presentation/shell/command_palette.dart` (`_dataEntries()`)
- **Problem:** Searching "احمد" and tapping the result jumps to the generic «طلبہ کی فہرست», not the record.
- **Fix:** Pass the query as a list-filter argument on jump, or label results as list-level.

### M5 — Finance IA has overlapping paths and an icon collision
- **Location:** `lib/presentation/shell/nav_destinations.dart`
- **Problem:** «طلبہ کی فیس» (`FeeManagementScreen`) vs «واجبات» (`FinanceHubSection.dues`) — two different screens for dues; and both «ڈیش بورڈ» and «مالی ڈیش بورڈ» use `Icons.dashboard_outlined`.
- **Fix:** Give «مالی ڈیش بورڈ» a distinct icon (`Icons.account_balance_outlined`); long-term, collapse fee-dues into one destination.

### M6 — Teacher sees two "students" destinations with different scope
- **Location:** `nav_destinations.dart` (mobile primary `student-list`, global) vs `role_home.dart` (`my-students`, teacher-scoped)
- **Problem:** Bottom-nav «طلبہ» shows the global list while the dashboard promotes «میرے طلبہ». Same label family, different scope — confusing.
- **Fix:** For teacher-family roles, point the mobile `student-list` primary at the teacher-scoped list (or relabel).

### M7 — Phone number "required" in the validator but optional in the actual guard
- **Location:** `lib/presentation/screens/students/student_dialogs.dart:183–196` (validator) vs `:252` (guard checks only name/fatherName)
- **Problem:** The field implies mandatory; the guard doesn't enforce it. Inconsistent data capture.
- **Fix:** Decide per field — label optional ones like پتہ (`(اختیاری)`), enforce the truly required ones (after C1).

### M8 — No result-count feedback when searching/filtering the student list
- **Location:** `lib/presentation/screens/admin/student_list_screen.dart:69` (header always shows unfiltered total)
- **Problem:** Searching «احمد» shows 3 rows while the header still says «کل 120 طالب علم» — no confirmation the filter applied. (`finance_dues_tab.dart:83–91` gets this right with an adaptive totals banner.)
- **Fix:** Show `'$filtered میں سے $total'` or a «$n طالب علم ملے» line under the search field — copy the dues-tab pattern.

### M9 — Fee-collection wizard: validation error is a detached snackbar, not an inline field error
- **Location:** `lib/presentation/screens/finance/collect_fee_screen.dart:440` (`_validateAmount` passed as `validator`, but no `Form` — result goes to a bottom `_snack` while the field sits mid-screen)
- **Problem:** Entering an over-remaining amount shows a floating message the user may miss; the field itself looks fine. The design system's `m360FieldDecoration` already has styled `errorBorder`/`errorStyle` waiting.
- **Fix:** Wrap the amount step in a `Form`, call `validate()` on «جاری رکھیں».

### M10 — Exam-type dropdown in results entry: required but unmarked, no hint; save stays enabled
- **Location:** `lib/presentation/screens/teacher/results_screen.dart:740–755`, `:912`
- **Problem:** `_entryExamType` starts null, no hint text, and the save button's disabled condition doesn't include it — failure surfaces only as a snackbar after tapping save.
- **Fix:** Pass `hint: 'منتخب کریں'` and include `_entryExamType == null` in the disabled condition (or default to the first option).

### M11 — Attendance "save" with zero changes claims success
- **Location:** `lib/presentation/screens/teacher/attendance_screen.dart:612–617`
- **Problem:** The sticky save bar is always enabled when a roster loads; with `_edits.isEmpty` it re-saves identical records and shows «حاضری کامیابی سے محفوظ ہو گئی».
- **Fix:** Disable the save CTA (or change its label) when `_edits.isEmpty`.

### M12 — No required-field marking anywhere in the sampled forms
- **Location:** Design system (`M360TextField`, `M360Dropdown` have no `required` param); `student_dialogs.dart`
- **Problem:** نام/والد کا نام are required but unmarked; پتہ is marked `(اختیاری)` — the convention exists but is applied asymmetrically.
- **Fix (design system):** Add an optional `required` param appending a red «*»/«لازم» marker to the Nastaleeq label; apply to the truly-required fields.

### M13 — Class times render in English ("03:45 PM") inside Urdu UI
- **Location:** `lib/core/utils/date_utils.dart:13–14` (`DateFormat('hh:mm a')`, no locale; `Intl.defaultLocale` never set)
- **Problem:** Inconsistent with the deliberate Urdu month names elsewhere (`attendance_screen.dart:409` uses `DateFormat('EEEE، d MMMM yyyy', 'ur')`).
- **Fix:** Pass `'ur'` explicitly in `formatTime`/`formatDateTime`; ideally `await initializeDateFormatting('ur')` at startup.

### M14 — Login CTA arrow points "back"
- **Location:** `lib/presentation/screens/auth/login_screen.dart:336` (`M360PrimaryButton(label: 'داخل ہوں', icon: Icons.arrow_back)`)
- **Problem:** The icon is leading (inline-start = right in RTL) and `arrow_back` auto-mirrors → points right, reading as "go back" on the primary *submit* action.
- **Fix:** `Icons.arrow_forward` (points left in RTL = forward).

### M15 — Forgot-password "back to login" uses the forward arrow
- **Location:** `lib/presentation/screens/auth/forgot_password_screen.dart:168` (label «لاگ ان پر واپس جائیں», icon `arrow_forward` → points left = "continue")
- **Problem:** Exact mirror-image of M14.
- **Fix:** `Icons.arrow_back`.

### M16 — Faint small label in the fee-collection hero
- **Location:** `lib/presentation/screens/finance/collect_fee_screen.dart:368–372` (`labelSmall` 12sp Nastaleeq at `Colors.white70` on primary-teal → ≈3.5:1, below AA 4.5:1; compounds H8)
- **Fix:** Full `Colors.white`, or bump to `labelMedium` size.

### M17 — Login keyboard flow: no next/done actions
- **Location:** `lib/presentation/screens/auth/login_screen.dart` (`_buildEmailInput`, `_buildPasswordInput`)
- **Problem:** `M360TextField` supports `textInputAction`/`onFieldSubmitted`, but the login fields don't set them — the keyboard shows a generic return key, focus doesn't advance email → password, and there's no keyboard submit.
- **Fix:** `textInputAction: TextInputAction.next` on email (focus password on submit), `done` on password (submit the form).

## Verified good (do not regress)

- **One design system, actually used**: `m360.dart` barrel with tokens, buttons, inputs, cards, dialogs, states, tables; no raw `DataTable` in presentation; `M360Table` auto-falls-back to card lists on narrow screens with horizontal scroll as last resort.
- **Confirmation discipline**: 23 files use `showM360ConfirmDialog` with consistent button order (cancel → confirm, danger-styled for deletes); typed confirmation for platform-level deletes (`platform_users_screen.dart:189`); every sampled delete/void is confirmed; students have no delete UI (active/inactive only).
- **States**: `M360LoadingState` skeletons, `M360ErrorState` with working retry, Urdu empty states with contextual actions («نیا طالب علم», «فلٹر تبدیل کریں»).
- **Success feedback in Urdu**: admission/edit/fee/attendance/results all confirm via snackbar; fee collection lands on a receipt step with a check icon; attendance has a sticky thumb-zone save bar with live counts and «سب کو حاضر کریں».
- **Fee-collection wizard**: 4-step indicator, amount pre-filled with remaining balance, «پوری بقایا رقم» shortcut, numeric keyboard + autofocus on the amount field, explicit review step before recording.
- **Navigation**: permission-first IA (`nav_destinations.dart`), one responsive pattern (right rail ≥1100px / drawer / bottom-nav + «مزید»), failsafe non-blank states, command palette (Ctrl+K) permission-filtered, logout confirmation dialog.
- **Dashboards**: task-oriented per role (principal «آج کیا کرنا ہے؟», teacher assignment-scoped, accountant plain-Urdu finance), 1-tap primary CTAs.
- **Localization**: zero hardcoded English `Text('…')` literals in sampled areas; strings centralized in `AppStrings`; Pakistani digit grouping (`3,80,000 روپے`); Urdu month names; `M360LatinText`/`M360Email` for LTR technical text, adopted in 9 screens; RTL pagination chevrons deliberately mirrored.
- **Typography policy**: explicit "Nastaleeq everywhere" with line-height ≥ 2.0 (no clipped nuqtas), Naskh fallback chain so Latin/digits never hit the system font.
- **Responsive**: 600/1100 breakpoints, `LayoutBuilder` column switching, max content widths, `Wrap` instead of overflow in page headers.
- **Contrast**: `textSecondary #757575` on white = 4.63:1 (AA); status chips contrast-engineered with documented ratios; meaning never color-alone.
- **Login**: password show/hide toggle with Urdu tooltip, autofill hints, honest "no self-registration" copy.
- **No placeholder screens**: every destination builder target verified; honest unavailable states.
